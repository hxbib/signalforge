# Evaluation changelog and failure analysis

Numbers live in `eval/results/*.json` and `eval/RESULTS.md` (generated by `eval/report.py`). This file records
what happened and why, by case id, so every statement can be checked against those files.

## Freeze
- Draw frozen by `eval/draw.py` before any arm ran: `eval/results/freeze.json` (seed = code SHA, corpus/inputs/gold
  sha256, per-case packet digests). Raw WDC files, packets and gold stay in `private/wdc/` (gitignored).

## Aborted attempt (no answers, not a run)
- The first v1 attempt was stopped after 7 calls. Every call failed inside our own SDK wrapper with
  `interaction returned no id` (coord/bugs/001: `store=False` interactions return no id; the wrapper treated that as
  a failure). No model answer was produced or read. Its log is kept privately

## v1 · what failed
Source: `eval/results/pairs-v1.json` (scored run) and `eval/results/diagnostic-v1.json`. The diagnostic is a post-hoc
re-run of the system arm's two calls on the v1 system-arm failures, done only to see which abstention rule fired. It is
not a score, and its model outputs can differ from the scored run.

- **The system arm made no wrong calls.** All of its v1 failures are abstentions on pairs whose gold label is `match`.
  Neither arm made a false accept on the 20 true non-matches.
- **Class 1: Carbon abstains when no manufacturer model number is printed** (pair-06, -09, -11, -20, -26, -38,
  -39). Typical cases are accessories and consumables with generic titles (a GoPro hand grip, Instax film twin pack, a
  Case Logic bag whose two listings are identical text), or colour/edition details on only one side. The PAIR prompt
  says "if decisive evidence is absent, abstain", and Carbon applies that, so it disagrees with Neon's tentative `match`
  and the pair abstains. The single-call baseline also abstains on most of these (see the paired counts). This is the
  intended conservative behaviour for identity tier `model_number`: the live app only promotes a listing on an exact
  printed model number, so abstaining here costs recall, not safety. We did not change it, because loosening it is
  exactly what would create false bargains.
- **Class 2: the verbatim-quote check rejects genuine quotes** (pair-25, pair-37). In pair-25 Neon collapsed a
  newline in the source (`…KitPart Number(s)\nOption…`) into a space. In pair-37 Carbon joined two verbatim fragments
  of a spec table with `...`. The check is a raw case-folded substring test, so both real quotes failed it and a
  correct `match` became an abstention.
- **Class 3: run-to-run variance** (pair-01). v1 abstained. In the diagnostic re-run both models said `match` with
  verbatim quotes. One sample per case cannot settle variance; we report it rather than re-scoring.

## Proposed change (the only one)
- `ASK @MODELS` (board, 15:57 ET): in `app.models.pair`, normalise whitespace on both the quote and the field before
  the substring test, and split a quote on `...` / `…` so that every non-empty fragment must appear verbatim on the same
  side. Text the model invents still fails the check. This targets class 2 only. Class 1 is left as designed.
- Status: see the bottom of this file. If the change lands before the 16:05 ET proof cutoff, v2 is run on the same
  frozen packets and reported beside v1 with each run's code SHA. Otherwise v1 is the result and the change stays a
  documented proposal. No other tuning on these labels.

## Status of the change (what really happened)
- 16:01 ET: the lead decided to act on the v1 numbers. On draw A the single Carbon call scored better than the two-model
  check with the same zero false accepts, and took about half the latency. Pair v2 (`PAIR_VERSION
  "v2-carbon-verified-quotes"`) makes the live listing check one Gemini 4 Carbon call followed by the deterministic
  verbatim-quote check, with the class-2 fix above (whitespace-normalised, fragment-wise on `...`/`…`). MODELS landed
  it at 16:02 and kept `app.models.pair_v1`. This change does two things at once: it drops the Neon stage, and it
  fixes the quote check. It is still the one change; we did no other tuning.
- **v2 on draw A is IN-SAMPLE.** The change was chosen after seeing v1 on these same packets. Only the system arm was
  re-run; the v1 baseline arm stands and was not re-run. Results are in `eval/results/pairs-v2.json`.
- **Held-out check.** To judge the change on data that did not suggest it, we drew 40 new pairs (draw B). Same strata,
  seed = sha256 of `eval/results/pairs-v1.json`, disjoint from draw A, frozen to `eval/results/freeze-b.json` before
  any call. Both arms ran on it. Results are in `eval/results/pairs-b-v2.json`.
- The outcomes, with each run's code SHA, are in `eval/RESULTS.md`, which `eval/report.py` generates from those files,
  including a generated plain reading. On every run so far, the system listing check equals or trails the single call
  on correctness, and neither arm has made a false accept. Read the listing-check result that way. The app's edge
  is not measured here; it is measured by the separate blind end-to-end benchmark (`e2e`).
- Bug 007 (rate-limit sleeps counted as latency) is fixed in `eval/run_pairs.py`. `ms` now covers the final attempt
  only and `wall_ms` is kept separately. v1 had zero 429 retries, so v1 latency was unaffected.
